# Stark World Engine Systems guide

Stark World Engine Systems adds data-driven gameplay systems to Stark World Engine. It is offline: no CDN, no network, no model calls.
It has three parts:

* **JS runtime** (`js/*.js`, about 5,700 lines): bundled with the child-safety word list into one inline script by
  `bundle.py` (about 400 KB).
* **Python side** (about 1,700 lines): the child-safety export gate, the `world.systems` schema, author-time
  procedural generation, the content-budget estimate, and the samples.
* **Tests**: `tests/test_stark_systems_*.py` (47 tests; the JS tests run in Node and are skipped when Node is absent).

Everything lives under one optional, versioned key, `world['systems']`, with `version: 1`. Worlds without it load
unchanged. Unknown fields are kept and warned about, never rejected. The full field list is in
`schema/systems.v1.schema.json` (JSON Schema, for the UE5 / Godot bridges). Editor panel specs (fields, types,
ranges, help text) are in `schema/editor_panels.json`, generated by `python -m stark_systems.schema --panels`.
The node catalog is `schema/node_catalog.json`.

**Child safety is part of every system and cannot be turned off.** See CHILD_SAFETY.md.

**Radiant quests** use 11 built-in templates: hunt, lone beast, fetch, deliver, explore, clear, gather, craft, escort,
rescue, survey. You can supply your own templates and pools; otherwise pools are taken from the world.

Variety guards:
* template cooldown;
* a cap on the same verb within a window;
* place, giver and target cooldowns;
* the same template / place / target combination never repeats;
* novelty scoring over 14 candidates;
* periodic follow-up leads.

Measured over 300 generated quests: no template ever repeats back to back, 9 verbs are used, no verb exceeds 30%,
and at least 90% of the recent window are distinct combinations. Children are never hunt or defeat targets; escort
and rescue of children are allowed because they protect them. Generated text goes through the child-safety check.

## Scripting

**StarkScript** is a JavaScript subset run by an interpreter. It does not use eval, so it works under strict CSP.

Supported: functions and closures, arrow functions, default and rest parameters, `let` / `const`, `if`, `for`,
`for-of`, `for-in`, `while`, `do`, `switch`, `try` / `catch` / `finally`, objects, arrays, spread, template literals,
`?.` and `??`. Not supported: `new`, classes, regex literals, `instanceof`, async.

Sandbox limits:
* scripts see only the game API: no `window`, `document`, network, storage or timers;
* `__proto__`, `constructor` and `prototype` are refused, and host functions are opaque;
* step budget (default 200,000 per call), call depth 120, 1M-character / element limits;
* a script is disabled after 20 errors, and errors are collected for the studio console.

Events: `on('name', fn)` or top-level `onStart`, `onUpdate`, `onInteract`, `onQuestStep`, `onQuestDone`, `onDamage`,
`onDeath`, `onEnterZone`, `onExitZone`, `onDialogueChoice`, `onCollect`, `onHour`, `onDawn`, `onDusk`, `onLevelUp`,
`onCraft`, `onWeather`. A script with `entity: id` only gets its own interact, damage and death events.

API: `world` (find / query / near / spawn / setWeather / setHour / raycast / player / hour / isNight), `self`,
`entity()`, `combat`, `ai`, `physics`, `inventory`, `quests` (incl. `generate`), `dialogue`, `factions`, `economy`,
`progression`, `ui`, `audio`, `camera`, `vars` (saved), `romance`, `appearance`, `after` / `every`, `rand` /
`randInt` / `pick`. Entity handles expose `x`, `y`, `z`, `rot`, `hp`, `name`, `team`, `tags` and methods. `age` is
read-only.

**Node graphs** (`systems.graphs`): 68 node types (events, flow, actions, data) compile to StarkScript through the
templates in `schema/node_catalog.json`. The same catalog is what the bridges map to Blueprints / GDScript. The
Python schema validates node types and links. The child-safety scan blocks harm nodes that target children (CS014).

## Scale

* **Streaming:** see the table above. The endless-world test generates more than 50 entities, drops pristine chunks,
  and holds the visible and awake-AI budgets.
* **Author-time generation** (`procgen.py`, baked into world.json so creators can edit it): `npcs` (families with
  names, jobs, traits, backstories, hourly schedules; children tagged child with fetch-quest hooks), `settlement` /
  `bake_settlement` (houses, lamps, NPCs, dialogue, kids' fetch quests; stays studio-valid), `dungeon` (BSP;
  every floor tile reachable), `region` (scatter with clearings).
* **Content budget** (`python -m stark_systems.content_budget WORLD.json`): an hours range built from counts
  (quest steps, enemies, dialogue words, level area, puzzle levels, laps, survival days) times a stated table of
  minutes, times a retry factor. Repeatable radiant quests are reported **separately**, counted only up to the
  distinct combinations. It is a model, not a measurement: calibrate it with playtests before quoting hours.

## Integration status (what is not done yet)

* The studio does not yet call any of this. The exact patches are in `INTEGRATION_PATCHES.md` (owned by the v28.5
  and bridge agents; verified on a temp copy by `tests/test_stark_systems_integration.py`).
* The studio's WebGL2 renderer does not yet draw GSYS genre worlds. They play in the reference player (canvas 2D +
  raycast). Worlds with `systems.player: 'gsys'` need a cartridge path that calls `GSYS.play`. The studio has no
  editor UI for the panels yet; `schema/editor_panels.json` is the spec.
* UE5 / Godot do not run these systems yet. The JSON Schema, node catalog and CHILD_SAFETY.md bridge section are
  the mapping spec.
* Not built: networking / multiplayer, a real 3D physics engine (the physics is 2.5D: plane + height), animation
  blending, audio mixing beyond synthesised cues, localisation tooling, touch / gamepad input in the reference player.
* The reference player was checked in headless Chrome (screenshots) and in Node simulations. No human has playtested
  the samples for fun or balance.
